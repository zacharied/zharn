## 1. The change

Two things ship together because the second only makes sense once the first is fixed.

**The character system prompt becomes stable for the life of a context.** Today it is a template
with phase, attended thread, owes, awaits and environment in it, rebuilt into the context's metadata
on every delivery and read once, at spawn. A live process never sees the rebuild. A respawn (crash,
Stop, app restart, recycle on an environment change) almost always gets a different prompt than the
one before, and the system prompt is the first block of the cache prefix, so every respawn is a cache
miss over the whole resumed conversation. Nothing architectural wants this; the situation line just
lives in the wrong place. The fix splits by volatility: stable facts in the system prompt, the
situation in the delivery message.

**Skills arrive.** `harness/skills/` becomes a Claude Code plugin holding five discipline skills
vendored from superpowers and four written for zharn. The meta skill is part of the stable system
prompt. The phase skill is volatile, so it never enters the system prompt: it rides in messages
only. `tests/skills/` proves delivery cheaply and records what the skills change on a real model.

## 2. The prompt model

### 2.1 System prompt: stable

Built at every spawn through a hook on the context store, the way placement already is: the story
store composes it from config, the role, and the skill files at that moment. It is never stored in
the context's metadata. Its parts:

- identity: name, character id, story key, story title;
- `being-a-character` (the file body);
- the CLI contract: the verb table and `$HARNESS_CLI`;
- the role's instructions and its outline rule (`outline_first` is per role, and a role is fixed for
  the life of a context, since a recast is a new context).

Everything in it is identical on every respawn of the same context. Bare contexts and asides keep
their stored prompt; theirs is already stable. Editing `config.py` or a skill file changes the next
spawn, which is what "your fork is your config" wants and what the stored copy was standing in for.

### 2.2 Delivery message: volatile

Every delivery opens with one situation line, then the comment as today:

```
[situation] phase implementing · attending #thr_x · you owe #thr_x · you await nothing · in zharn at /path
[Zach] reply in #thr_x: use sqlite
```

The "Phase is now X" line goes away; the situation line carries the phase. A message appends to the
conversation and never disturbs the prefix.

### 2.3 The phase skill rides in messages

The rule is not "did this action cross a phase" but "does the story's phase differ from the last one
this character was told". The character record gains one key:

```
Character.phase_seen: planning | implementing | null
```

The inbox is why: a comment posted before Proceed can be popped after it, and the action-time
`phase_before` would miss the crossing. Cases:

| Moment | What the character receives |
|---|---|
| Fresh context, recast included | First message = brief + the current phase skill; `phase_seen` set. |
| Forked friend | No brief; `phase_seen` copies from the source, whose conversation already holds the skill. |
| Any delivery with `phase != phase_seen` | The new phase's skill appended after the comment; `phase_seen` updated. |
| Cast `proceed` | The `implementing-a-story` body on stdout; `phase_seen` updated so the next delivery does not repeat it. |
| Respawn mid-phase | Nothing: the resumed conversation already holds the skill. |

Friends get the phase skill like the protagonist. The story's phase binds everyone on it: a friend
called in planning does not edit files either.

Deliveries in terminal phases carry no skill (retired characters receive nothing anyway).

## 3. The skills tree

```
harness/skills/                         # config.SKILLS_DIR; one Claude Code plugin
  .claude-plugin/plugin.json            # name "zharn"
  VENDORED.md                           # source: superpowers 6.3.0; per-file list of edits
  skills/
    being-a-character/SKILL.md          # meta; in the system prompt; < 150 words
    planning-a-story/SKILL.md           # phase
    implementing-a-story/SKILL.md       # phase
    delegating/SKILL.md                 # minion · friend · sub-story
    test-driven-development/            # vendored: SKILL.md, writing-good-tests.md
    systematic-debugging/               # vendored: SKILL.md, four technique docs, find-polluter.sh
    verification-before-completion/     # vendored
    receiving-code-review/              # vendored
    requesting-code-review/             # vendored, adapted: SKILL.md, code-reviewer.md as the call note
LICENSES/superpowers                    # MIT, Jesse Vincent
```

Every spawn passes `--plugin-dir <SKILLS_DIR>`. Claude lists the skills as `zharn:<name>`.

Not copied from the vendored directories: `CREATION-LOG.md` and `test-pressure-*.md` under
systematic-debugging (the author's own test artifacts).

### 3.2 Adaptation rules

Applied to every vendored file and listed per file in `VENDORED.md`:

- `superpowers:` → `zharn:`; references to skills that are not vendored are removed or pointed at the
  zharn replacement;
- "your human partner" → "the thread's author" (the author of a thread may be a character);
- "subagent" / "Task tool" → minion; "dispatch a subagent to review" → `call` a friend;
- `TodoWrite` references are left alone (the tool exists under `claude -p`).

Nothing else changes. The next upstream sync is a diff against 6.3.0.

### 3.3 The zharn-native skills

All four use superpowers' skeleton: iron law, hard gate, rationalization table, checklist, a
flowchart only at a decision point; descriptions are triggers, never workflow.

**being-a-character** (system prompt, under 150 words). Iron laws: (1) never stop while you owe a
thread unless a friend or a sub-story is out; the harness will yield for you and say so. (2) Status is
not yours to set. (3) Everything you say to anyone is a comment. (4) The phase skill in your
conversation is mandatory; re-read it with the Skill tool when unsure. (5) When told your context
is low, `recap` before anything else. (6) Questions carry options and are batched into one yield;
handoffs carry evidence: what changed, how verified, where to look first.

**planning-a-story.** Classify: spike (minions read, then `yield --handoff` the answer), bounded
(`proceed`), or outline (ask everything you must in one `yield --question`, then `yield --handoff`
the outline, then wait for Proceed). Hard gate: no file edits while planning. Rationalization table
entry that matters most: "one question at a time" is a rule from another harness; a yield ends your
turn, so batch. What an outline contains: the steps, the files, the tests, what will be delegated
and to whom.

**implementing-a-story.** REQUIRED sub-skills: test-driven-development,
verification-before-completion, delegating. Protect your context: minions read, friends build, you
hold the plot. A review by a friend after each delegated task. Handoff body: what changed, how
verified, where to look first; the checks ride along mechanically.

**delegating.** The §6 table of AGENT-MODEL.md (minion when nobody needs to see the process; friend
when the contribution should be visible; sub-story when the work should be described and validated
on its own), plus: reviews are always friends; independent tasks go out at once, dependent ones in
order; `wait` after casting.

## 4. Tests

### 4.1 Cheap layer, fake claude

The fake echoes its argv in the init event, so a test can see `--plugin-dir`. It records the
`--append-system-prompt` value the same way. Assertions:

- the system prompt of a character holds identity, the `being-a-character` body, the contract, the
  role's instructions, and none of: phase, attention, owes, awaits, environment;
- two consecutive spawns of one context get byte-identical system prompts, across a Proceed in
  between;
- every delivery starts with a situation line carrying the current phase, attention, owes, awaits,
  environment;
- the first message of a fresh context ends with the phase skill; a fork's does not;
- a delivery after Proceed, after Back to planning, and after Reopen appends the new phase skill,
  once; an inbox item popped after a Proceed appends it; a delivery in the same phase does not;
- cast `proceed` prints `implementing-a-story` and the next delivery does not repeat it;
- a friend cast in implementing receives `implementing-a-story` in its first message.

### 4.2 Paid layer, real claude

`tests/skills/<scenario>/` holds `prompt.md`, a fixture repo builder, and `expected.json`: the
verbs the scenario must and must not produce. The runner spawns a character with and without the
skill under test and reads `verbs_log`, never transcripts. It runs only under
`HARNESS_PAID_TESTS=1`; the recorded baseline and skilled `verbs_log` of the last run are committed
beside the scenario as evidence. Three scenarios:

| Scenario | Without the skill | With it |
|---|---|---|
| outline-before-proceed (role `outline_first`) | `proceed` rejected, or edits while planning | one `yield --question`, then `yield --handoff`, no edits |
| handoff-not-silence (implementing, small task) | turn ends with no yield; the harness yields | `yield --handoff` with evidence |
| batch-questions (planning, three unknowns) | three yields in a row | one yield with options |

## 6. Deferred

- **Situation reporting.** The line is emitted on every delivery. It could shrink to the fields
  that changed since the last delivery, or be dropped on a mid-turn push into the attended thread
  where nothing has moved. Do it once there is evidence the line costs attention or tokens.
- `writing-skills` (position 3), and `yielding` as its own skill if the paid scenarios show the
  iron law is not enough.
- Context-usage tracking and auto-recast stay deferred from slice 3; nothing here depends on them.

## 7. Stress cases

Each is a test in §4.1 or a line in the spec.

- **Back to planning with a live process.** The protagonist is mid-implementing, the author presses
  Back to planning. The process is alive and keeps its prompt; the delivery carries the situation
  line with `phase planning` and appends `planning-a-story`. Works because the skill is a message.
- **Proceed, then an inbox pop.** A friend's comment queued during planning is popped after
  Proceed. `phase_seen` is still planning, so the pop carries `implementing-a-story`.
- **Recast mid-implementing.** New context; the brief is the first message and ends with
  `implementing-a-story`; `phase_seen` set. Nothing bespoke.
- **Fork in planning.** The source has `phase_seen = planning`; the fork copies it and gets no
  skill; its conversation already holds one.
- **Crash and respawn.** Same session resumed, same system prompt bytes, no skill sent.
- **Reopen.** Terminal to implementing; `phase_seen` was implementing or planning; the note's
  delivery carries `implementing-a-story` if it differs.
- **An `outline_first` role recast into one that is not.** New context, new role, new system
  prompt. The outline rule is in the prompt, so it changes with the role, as it should.
